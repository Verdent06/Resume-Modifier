# Software Engineering Intern, Summer 2027 at RTX / Raytheon

## Role Summary

Summer 2027 onsite SWE intern on a Raytheon development team in Marlborough, MA that develops, integrates, tests, and documents hardware/software platforms. The intern writes software to integrate components and add capabilities, integrates applications from many sources and holds them to performance/stability/utilization standards, and follows accepted engineering process: unit tests with high code coverage, code peer reviews, design reviews, and test plans. The JD surface is general software development in a Unix/Linux, C/C++/Java environment; the company identity adds a mission-critical real-time systems lens — the software supports missiles, launchers, radars, and naval/fire-control, so real-time systems, DSP, ML/autonomy, cyber, and DevOps are the domains this org lives in, and reliability/test discipline is the culture.

## Track Decision

- **screen_track:** full-stack (general SWE)
- **differentiator:** real-time / DSP / embedded systems depth for mission-critical defense platforms (C/C++ systems engineering + integration & test rigor)
- **track_divergence:** false

The screen spine is general SWE per `recruiting.md` Part III §11 and `resume.md` Part III §12: the required qualifications test broad software development (Java in Unix/Linux, integration, unit testing, code/design review, test plans), not ROS/perception/controls as hard requirements — so this is not the robotics track and not an ML-research track despite the org's ML/autonomy mention. The differentiator (hard real-time / DSP / low-level C++ systems discipline, the domain the org actually builds in for radar/fire-control) is **flavor on that spine, not a second track** — the same call as the CTC trading-tech precedent, where low-latency systems depth is a differentiator on a general-SWE screen rather than a track flip. The strongest page leads with the general-SWE spine (shipped software, integration, test discipline, polyglot fluency shown in bullets) and keeps the hard real-time / DSP / low-level C++ project prominent (lead Project, immediately after Experience) and deep — it does not become a pure audio-DSP specialist page, and it does not pivot to an ML-systems page. Do not reorder Projects ahead of Experience to chase the differentiator; Experience-before-Projects holds.

## Screen Criteria

- JD languages demonstrated **in bullets**, not Skills-only — especially C/C++ (on-domain for real-time/DSP) and Python (preferred scripting); Java is the one required language, and honest presence beats fabrication when the work isn't there.
- Real-time / low-level / systems engineering depth that reads as mission-critical-adjacent: concurrency, latency, memory discipline, deterministic behavior, or DSP — the domain the org builds in.
- End-to-end software development with integration and **test discipline** visible: unit tests, CI, code coverage, or a release/verification gate — the JD names these explicitly.
- Shipped, owned software with real outcomes (production users, measurable performance/reliability wins), not tutorial-grade demos.
- Preferred-stack coverage shown through use: Python scripting, Git, a JS framework (Angular/Vue), and CI (Jenkins/Maven/GitLab-adjacent).
- Unix/Linux-environment software development signal where the work supports it.

## Anti-Patterns

- Screening as an ML-research or pure-robotics intern because the org mentions ML/autonomy — the requirements test general SWE + systems + test discipline.
- A JD language named in Skills with zero bullet evidence at a company where that language is a floor signal (keyword smell).
- Real-time/DSP work framed as a hobby-audio demo with no engineering rigor or ownership, rather than as mission-critical-adjacent systems engineering.
- Metric-free "shipped X" claims where the org's whole culture is stability, performance, and test coverage.
- Thin single-bullet filler entries that dilute a strong systems + shipping spine.
- Frontend-only or notebook-only framing with no integration, testing, or systems depth.
