# Software Engineer Intern, Backend (Summer 2027) at Lyft

## Role Summary

A Summer 2027 paid backend internship in San Francisco (hybrid Mon/Wed/Thu). Interns own a scoped production project, check in throughout the day, leave code better than they found it, back reliability with unit / integration / load tests, sit in code reviews, and ship through CI/CD onto surfaces that affect drivers and passengers. The JD surface is generic backend SWE intern: CS fundamentals, testing, communication, databases, real-time problems, optional mobile and OSS — no named language. Company identity is a two-sided rideshare marketplace: live matching and dispatch under location and concurrency pressure, not a CRUD web app and not an ML internship.

## Track Decision

- **screen_track:** full-stack
- **differentiator:** rideshare marketplace / realtime backend / driver–passenger marketplace
- **track_divergence:** true

The literal requirements test general SWE / full-stack fundamentals (shipped services, APIs, a database, testing, CI/CD) — not ML training, ROS, or SRE specialization — so the resume spine is full-stack / general SWE with backend depth. Lyft's memorable company-fit signal is real-time marketplace backend: latency, concurrency, reliability under live two-sided load. The resume leads with the full-stack spine **and** keeps real-time / systems / marketplace-shaped evidence prominent and deep in the top half. It does not collapse into a pure frontend page, a notebook-ML page, or a rideshare-domain claim the work cannot support.

## Team & Bar

The reviewer is filling a small B-tier intern cohort (~3–5% estimated acceptance; `companies.md` bottleneck: tech rounds) ahead of a CodeSignal-class OA (Extern/cycle reports also cite CoderPad or HackerRank) and a practical laptop / coding loop that grades correctness, clean code, and performance. Resume job: survive the 7-second Greenhouse scan and win team-match after the OA. Signals that win: languages demonstrated inside bullets, not Skills alone; shipped APIs and databases with testing or CI in the narrative; real-time / latency / concurrency proof; impact metrics that size outcomes (latency, failure recovery, throughput, cost) rather than vanity counts. Recruiter voice: CS fundamentals plus engineers who communicate daily and care that the work hits drivers and passengers. Passion for community, sustainability, or transportation is a plus, not a substitute for engineering.

## Screen Criteria

- JD languages are unnamed; still require polyglot proof in bullets — Python and at least one other inventory language used in an architectural decision, not Skills-only.
- Backend delivery: services or APIs, a real database, and a deploy/CI path, with at least one product defensible layer-by-layer (why this store, what failed, how it was tested or recovered).
- Testing / reliability / CI evidence on the page (unit, integration, load, or e2e; GitHub Actions or equivalent) — the JD treats testing and CI/CD as how work ships, not a Skills footnote.
- Real-time or concurrency / latency evidence visible in the top half (company-fit differentiator) without turning the page into a DSP specialist resume or burying systems work under GTM/consulting filler.
- Impact metrics (latency, throughput, failure recovery, cost, scale) at roughly one per two bullets; titles that the bullets can support.
- Anti-patterns: leading with LoRA / LangGraph / agentic-AI framing as if this were an ML internship; club-ops without engineering; Skills-list databases or testing with zero bullet evidence; GTM/deal-sourcing as the lead at a marketplace-backend company; claiming mobile or OSS depth the page does not show; inventing marketplace/rideshare domain work.
