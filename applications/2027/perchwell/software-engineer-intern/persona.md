**Pass signals (abstract):**

- Web application from data layer to front end: a relational datastore or SQL, an API/backend, and a frontend framework demonstrated in bullets — not Skills-only (`resume.md` §12). Breadth across the stack plus depth in at least one layer.
- JD-listed languages the candidate actually has (**TypeScript**, **SQL**) used inside architectural decisions. **React** through use is a named bonus. A web application framework through use (Rails if honest; otherwise a real server framework the page can defend). Do not treat Ruby/Rails as present when it is not.
- Evidence of owning a scoped product (architecture + implementation decisions, production features, a named bug fix) over club-ops or GTM-only lead stories.
- Technical collaboration / communication visible in how work is described (mentor-scoped intern; PM/design-adjacent shipping; final presentation).
- College leadership if it is engineering-adjacent (founded product, titled ownership) — bonus, not a substitute for the stack.
- Class-year on page shows current enrollment (`Expected May 2028` → rising senior at June 2027 start; eligible). U.S. work authorization is a form/knockout, not a resume line.

**Anti-patterns:**

- Skills-list TypeScript / SQL / React with zero bullet evidence at a shop where data-layer-to-frontend is the floor.
- Invented **Ruby on Rails** (or Express / Django as if this were the 2026 copy).
- Routing the page to research-only LoRA / notebook ML because the product is "AI-powered."
- Lead entry that is off-axis for product web engineering (pure GTM scoring, low-level DSP with no API/UI spine) while the full-stack shipping story is buried.
- Thin single-bullet filler that dilutes a shippable production-product story.
- Club-ops without engineering depth (`resume.md` §8).
- Keyword stuffing MLS / listings / proptech in Skills with no supporting system.
- Vanity metrics (uptime, LOC, coverage %) standing in for impact (`resume.md` §4).
