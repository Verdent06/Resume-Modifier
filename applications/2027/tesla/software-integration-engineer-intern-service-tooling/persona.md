# Software Integration Engineer Intern – Service Tooling (Winter/Spring 2027) at Tesla

## Role Summary

A Winter/Spring 2027 intern on Tesla's **Service Tooling** team in **Fremont, CA** (req **286127**). Full-time on-site, **40 hours/week**, minimum **12 weeks**, start **January 2027** through ~May 2027 (or into Summer 2027 if offered). The intern writes software that technicians use to service and maintain Tesla vehicles, including Robotaxi: software for service-tooling **equipment**, integration with **hardware and automation**, hands-on **test and debug** with engineering and service technicians, and documentation. JD surface is general SWE plus hardware-adjacent integration: currently pursuing CS / Mechatronics / EE or related; **Python, C++, or SQL** through coursework or projects; data structures and algorithms; first-principles problem-solving. Preferred: prior internship or student projects (Robotics Club, coding competitions); testing methodologies and design patterns; **hardware integration or embedded systems**; interest in automation, robotics, or ML. This is **not** Autopilot/FSD model training, **not** Vehicle Engineering Design Technology (req 279763), **not** Applications Engineering (req 280820), **not** Factory Firmware, **not** Battery Management Systems, and **not** Tesla Energy UI. Existing `applications/2027/tesla/company.md` describes a sibling Design Technology intern — this req is Service Tooling in Fremont.

## Screen Criteria

**Pass signals (abstract):**

- Demonstrates at least one JD-floor language through use in bullets — **Python, C++, or SQL** — not Skills alone. Claiming C++ or SQL on the Skills line with zero use is a polyglot ding at a hardware-adjacent team.
- Shows shipped software other people run (internal tools, stakeholder APIs, release artifacts) — analog to "software solutions for service tooling equipment" and "technicians rely on every day."
- Shows hands-on **testing and debugging** with a sized before/after (failure rate, latency, qualification, hours saved) — maps to "testing and debugging of your code in collaboration with engineering and service technicians."
- Makes **hardware-adjacent / embedded / real-time / integration** evidence visible in the top half of Projects (or otherwise prominent): constraints, lock-free or zero-allocation paths, release/test checklists, multi-system integration — without fabricating vehicle firmware, CAN, ROS, or Robotaxi work.
- Keeps **technician-tooling / automation** identity visible: tools that capture a process, integrate systems, or recover from a defect — not a consumer-SaaS page that never shows operated tools.
- Uses impact metrics (latency, failure recovery, hours, scale) rather than vanity counts (`resume.md` §4).
- Class-year on page: `Expected May 2028` plus a January 2027 start is junior-year winter/spring with return to school. JD has no numeric graduation-window cutoff beyond current enrollment.

**Anti-patterns:**

- Invented ROS, CAN, vehicle firmware, Robotaxi, manufacturing (machining/welding), Linux sysadmin, Go, Rust, or a service-center internship.
- Leading with LoRA / LangGraph / agentic-AI as if this were Autopilot or applied-ML.
- Skills-only C++ or SQL at a team that prefers hardware integration / embedded.
- Club-ops or GTM/quant deal-sourcing as the lead story for a service-tooling intern.
- Frontend-only with no integration, test, or deploy path.
- Treating this req as Design Technology, Applications Engineering, Factory Firmware, or BMS.
