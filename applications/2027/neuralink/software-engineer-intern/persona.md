# Software Engineer Intern, Implant at Neuralink

## Role Summary

A paid, on-site software internship on Neuralink’s Brain Interfaces Software Team (Austin, TX or South San Francisco, CA; $35/hr CA transparency). The intern develops and maintains the implant software stack: Implant and Charger SDKs, firmware build tooling, manufacturing-line acceptance software, design-control verification tests, and implant recorder / monitoring systems. The JD surface is generic SWE — Python plus C or Rust, Linux/Unix, exceptional ability, first principles, production-vs-research intuition — not an ML-training or ROS posting. Company identity is implantable BCI hardware and the safety-critical software around it: communication, verification, manufacturing, and monitoring that must be production-grade.

## Team & Bar

The reviewer is a Greenhouse human screener at an Unrated, Musk-adjacent BCI company (no `companies.md` row; nearest peers SpaceX / Tesla / Medtronic). There is no named intern OA platform; the binding front door is the exceptional-ability essay (3–4 quantitative problem/solution/result examples — “the most important part of our interview process”) plus a human PDF read. Recruiter voice: can this intern architect and ship elegant, reliable software with autonomy, and do they have intuition for production systems rather than research-grade prototypes? Strong signals: JD languages demonstrated inside bullets (Python required; C or Rust if present — exceptional engineering matters above a language hang-up); Linux/Unix comfort shown through real tooling or systems work; metrics that size reliability, latency, failure recovery, or manufacturing/verification-style correctness; visible real-time / memory / concurrency / test discipline so the page is memorable past a generic web resume. Prestige is a tiebreaker (`recruiting.md` §8). Work-auth / sponsorship and on-site self-relocate are form knockouts, not resume lines.

## Screen Criteria

- JD languages shown through use in bullets — Python at minimum; C or Rust if the page can support them — not Skills-list only. A C-family systems language used in a real-time or production constraint is a credible adjacent signal when literal C/Rust is absent; Skills-only C/Rust claims fail.
- Production-vs-research intuition on the page: shipped systems others depend on, reliability/failure-recovery, verification or test discipline — not notebook ML or demo-only research.
- Linux/Unix / command-line / build-tooling fluency shown through use (tooling, CMake, deploy, CLI-adjacent work), not a Skills token.
- Differentiator visible in the top half: real-time constraints, memory/concurrency safety, hardware-adjacent or safety-critical-adjacent discipline — without turning the resume into a fabricated implant-firmware or medical-device internship.
- Impact metrics that size outcomes (latency, cost, failure rate, scale, hours saved) rather than vanity counts.
- Anti-patterns: club-ops filler; Skills-only language claims; a pure agentic/LLM product page with no systems or production-reliability evidence; notebook ML; metric-free architecture claims; claiming C, Rust, firmware, or safety-critical medical-device work the page cannot defend.
